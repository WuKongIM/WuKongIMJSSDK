## 联调发现并修复的问题

1. 服务端由在线设备路由构造提示投递路由时遗漏 `DeviceID`、`DeviceFlag`、
   `DeviceLevel`。真实浏览器收到协商确认，却收不到编辑提示。新增测试在修复前，
   本节点与 RPC 转发场景均失败；补齐身份后通过，过期设备身份仍被拒绝。
2. 本地 SENDACK 的消息 ID 是 BigNumber，示例须用 `toString()` 转成精确字符串。
3. 编辑前的版本校准使用包含目标序号的向上查询范围，避免读取到相邻消息。
4. 编辑提示引起的预览刷新只合并匹配的最后消息正文，不导入并发读取返回的未读数和排序字段。

测试明确要求收到目标消息和版本的真实 `message_updated` EVENT，不能仅凭初始补拉
恰好读到新内容判定提示链路成功。

最终联调输出 `result=passed`、`browserVerified=true`、`backgroundErrors=[]`；
两组提示等待样本分别为 3934 ms 和 11877 ms。该次原始日志与截图保存在运行机的
临时目录 `/var/folders/q8/sn__8sjn6z318y0s4scxjq240000gn/T/wk-js-edit-pOYfGW`，
不随 npm 包分发。

## 性能与适用边界

- 测试拓扑为单节点集群，256 个 Hash Slot。RPC 转发由单元测试覆盖，未运行真实多节点联调。
- 1000 个非当前频道的提示在合成测试中只合并为一次最近会话读取，不产生 1000 个频道编辑读取。
  这是请求数量约束验证，不是大群负载测试。
- 当前频道同步串行、历史请求排队上限 8、每波最多 20 页后让出执行、单页请求 100 条；
  默认消息缓存上限 1000 条或约 8 MiB，结果未知的编辑请求最多保留 32 个。
- 最近会话标准适配器默认只刷新一页 100 条；多页目录由业务 Provider 维护。
- 多次本机联调观察到真实提示等待约 4–12 秒，受服务端后台任务发现机制影响。
  尚未做高并发、大群、CPU/内存曲线、长时间稳定性或 p95/p99 时延验证，不能把这些样本当作 SLA。
- 下一项性能工作应测量并优化服务端提示任务发现时延，保持任务恢复与集群语义；
  本次没有给 SDK 增加周期轮询来缩短表面等待时间。

复现命令及宿主要求见 [接入文档](message-editing.md#运行示例与验证)。
